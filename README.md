# Consultant Chat

Тестовое задание: страница `/chat` со списком встреч (SSR + TanStack Query) и чатом по WebSocket.

## Требования

- Node.js 20+ (проверялось на 20 и 24);
- pnpm 10 (версия зафиксирована в `packageManager`, включается через `corepack enable`).

## Запуск

```bash
pnpm install
pnpm dev:all   # поднимает и Next.js, и echo-сервер сразу
```

Либо по отдельности:

```bash
pnpm dev          # Next.js — http://localhost:3000
node server.js    # WS echo-сервер — ws://localhost:8081 (то же самое: pnpm ws)
```

WS-адрес переопределяется через `NEXT_PUBLIC_WS_URL` (см. `.env.example`), по умолчанию — `ws://localhost:8081`.

Страница: [localhost:3000/chat](http://localhost:3000/chat)

Проверки:

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

## Что где лежит и почему

Встречи рендерятся на сервере — `app/chat/page.tsx` делает `prefetchQuery` напрямую через `getMeetings()`, без похода по HTTP на собственный же роут, и отдаёт кэш через `HydrationBoundary`. Поэтому список виден в HTML даже без JS. Кнопка «Обновить» после гидрации уже работает как обычный TanStack Query — стучится в `/api/meetings`.

Граница server/client: `page.tsx` и корневой layout — server, всё интерактивное (сам чат, кнопка обновления встреч) — client, потому что там стейт, эффекты и WebSocket. Ничего лишнего в client не тащил — провайдер для React Query вынесен в отдельный тонкий компонент, чтобы не помечать `'use client'` больше, чем нужно.

Чат — `useReducer` с чистым редьюсером (`features/chat/model/reducer.ts`), а весь WebSocket-быт — в отдельном хуке. Сообщение сразу появляется в ленте как `queued`, при разрыве связи «зависшие» `sending`-сообщения возвращаются в очередь. Основной путь досылки — автоматический: как только сокет открылся, `flushQueue` отправляет всё, что осталось в очереди. Кнопка «Повторить» — ручная подстраховка на том же пути, поэтому она активна только при живом соединении (без связи нажимать было бы некуда). ID при повторной отправке не меняется — он и есть ключ дедупликации.

Дедупликация двусторонняя: `pendingIds` не даёт отправить один и тот же id дважды в одном соединении, а редьюсер игнорирует повторный echo, если ответ консультанта для этого id уже есть.

Reconnect — экспоненциальный backoff с джиттером: 1s → 2s → 4s → 8s → 10s (дальше потолок 10s), счётчик сбрасывается на успешном `open`.

## Ограничения

- Это at-least-once, не exactly-once — сервер ничего не подтверждает отдельным ack и не хранит состояние, так что железной гарантии единожды-доставленности тут не будет в принципе.
- Очередь сообщений живёт только в памяти вкладки, обновление страницы её стирает.
- Echo-сервер сам рвёт соединение раз в 25-35 секунд — это специально, так проверяется reconnect.
- Встречи захардкожены, обновление их не меняет, просто перезапрашивает.
